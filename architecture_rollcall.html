架構目錄

🗺️ 系統總體架構

林口教會點名與出席系統採用前後端分離的輕量化三層式快取架構。前端靜態網頁託管於 GitHub Pages，後端利用 Google Apps Script (GAS) 做為資料邏輯處理引擎，並將 Google Sheets 做為主要資料庫。為了大幅提升效能並降低 GAS 的配額上限消耗，引入 Firebase Realtime Database (RTDB) 作為高效能快取層。

💡 設計核心： 由於大部分請求為唯讀操作（如取得名單、讀取歷史圖表），Firebase 快取命中速度約 50ms（相較於直接呼叫 GAS 耗時 2~5 秒），為使用者提供極速的載入體驗，同時降低 GAS 額度消耗高達 80% 以上。

⛪ 主日出席點名系統

主日出席點名系統是教會的核心，負責記錄每週主日崇拜中不同語系、場次、主日學班別的出席人數，並做為全教會會友名單的「單一真實來源 (Single Source of Truth, SSOT)」。

🌟 關鍵核心功能

  • 會友資料庫 (Master Members)：包含會友的姓名、性別、系統編號及專屬的 QR Code，不將「小組/身分」欄位交由主日單獨修改，而由小組系統同步與主日連動。
  • 二維碼/個人名卡生成：自動將會友的「系統編號 (如: LK00001)」編碼為 QR Code，利用 Google Slides 模板批次產出精美的個人名卡，儲存在 Google Drive 中供列印。
  • 場次分級與智慧點名：點名介面支援「華語」、「台語」、「聯合」、「主日學」等分區。手機或掃描器刷 QR Code 時，後端 syncClickToServer 會即時寫入，並保證多裝置、多點即時同步。
  • 數據趨勢分析：提供出席人數統計、出勤率排行榜以及長期出席趨勢圖表。

👥 小組點名系統

小組點名系統旨在協助各個小組長或輔導輕鬆管理小組日常聚會出勤。系統特別設計了代碼認證機制，讓小組長只需輸入小組專屬代碼（如: A01）即可登入該小組，不需要複雜的帳號密碼登入。

🌟 關鍵核心功能

  • 代碼快速登入 (Code Authentication)：在登入頁輸入專屬代碼即可鎖定該小組。另設有最高權限管理者密碼（預設為 LK31），可管理所有小組及檢視全小組統計。
  • 與主日名單智慧連動：新增組員時，系統會調用 getMemberSuggestions 從主日 Master 名單載入會友候選，避免手打打錯或同音字造成的混亂。當從小組名單中移除組員時，會自動同步修正主日 Master 名單中的「所屬小組與身分」欄。
  • 小組專有設定 (拖曳與暱稱)：小組長可以自由對組員名單進行拖曳排序（採用 Sortable.js 手把 ⋮⋮ ），並且可以為組員加上小組內專屬的暱稱（如：小美），在點名介面會以 姓名 (暱稱) 形式呈現。
  • 完美隔離陪伴同工：由於陪伴同工（如牧長、輔導）會列席多個小組，在計算小組「出勤率」與「統計報表」時，後端會自動排除角色為「陪伴同工」的成員，以反映真實組員出席率。
  • 保留歷史出席紀錄：如果某成員已離開小組或被移除，只要他在歷史的某一聚會天有出席，在查詢該天單日點名統計時，他仍會正確列在出席名單上，並標註為 (歷史)，確保歷史數據不受影響。

🔌 API 與快取機制

本系統使用 Firebase Realtime Database (RTDB) 架設高速唯讀快取層，核心原理為：在寫入（CRUD）時進行主動快取失效 (Active Cache Invalidation)。前端的 config.js 與後端 GAS 皆整合了對應的 Invalidation 流程，以確保資料在極速讀取的同時，維持強一致性 (Strong Consistency)。

⚠️ 安全提醒： Firebase 的 Web API Key 公開於 firebase-config.js 中。為了防止盜用，此 API Key 已在 GCP Console 啟用 HTTP Referrer 限制，僅允許 jirehwang.github.io/* 的請求呼叫。此外，RTDB Rules 限制為 "cache.write = auth != null"，前端唯讀，只有擁有 Service Account 的後端 GAS 可以寫入/更新。

🔄 三層式快取失效 (Invalidation) 機制

  1. 第一層：前端失效 — 當前端呼叫寫入 API 時（如 updateMember），config.js 中的 _INVALIDATE_ON_WRITE 規則會自動清空 Firebase 中所有相關 Read API 的快取。
  2. 第二層：後端 GAS 失效 — GAS 的寫入業務函式（如 updateGroupInfo）在完成 Google Sheets 的寫入後，會同步呼叫 firebaseInvalidate([...])，主動刪除快取。
  3. 第三層：Sheets 試算表 onEdit 失效 — 如果管理員直接在 Google Sheets 試算表中手動修改資料，Sheet 的 onEdit Trigger 會捕捉此變動，並透過 FirebaseSync.js 清空對應的快取區塊。

⚡ GAS 內部 CacheService 機制

除了外部的 Firebase 快取外，GAS 內部也建立了 CacheService 機制（由 CacheManager.js 管理）。在同一次 HTTP 請求，或是極短時間內（TTL 設為 5.5 小時），若有多個函式都需要取得會友名單，會優先從 GAS 本地的 CacheService 讀取，以極大化降低 Sheet I/O 次數，避免觸發 Google 的試算表併發讀取限制。

為了防止冷啟動延遲，系統設定了 keepWarm 排程，每 4 小時會自動喚醒 GAS 並重建 CacheService 快取，確保執行時永遠處於熱機狀態。

🗄️ 試算表資料結構

系統資料分佈在兩個 Google Sheets 試算表中：主日出席試算表與小組點名試算表。兩者透過系統編號（UID，格式如 LK00001）進行對應關聯，避免因改名或重名造成的點名歷史錯亂。

B (Col 2) 性別 字串。男 / 女。

🛠️ 部署與維護手冊

本系統的前端與後端部署在不同的位置。開發與日常運維請遵循以下工作流：

1. 前端部署 (GitHub Pages)

前端專案位於 Github/LKC1958_June_1.github.io 本地目錄中。

  1. 修改 HTML/CSS 或 config.js 後，確認本地測試無誤。
  2. 提交並推送到 GitHub： 
    git add .
git commit -m "feat: 更新點名系統功能"
git push
  3. GitHub Pages 自動發布後，即可在 https://jirehwang.github.io/LKC1958_June_1.github.io/ 檢視更新。

2. 後端部署 (Google Apps Script)

後端 GAS 使用 clasp 工具在本地與雲端進行同步與版控。專案檔案位於本地 LKC/主日出席_測試版/ 目錄。

  1. 在本地修改 .js (在 GAS 雲端即為 .gs) 檔案。
  2. 在該專案目錄下開啟終端機，執行 clasp 推送： 
    clasp push
  3. 若要部署為新版本，可執行： 
    clasp deploy
    並將產生的新網址更新至前端 config.js 的 _URL_ROUTER 中。

3. 維護人員專用 GAS 診斷函數

在 GAS 編輯器中，維護人員可以手動執行以下特定函數以完成初始化或排除故障：

  • setupKeepWarmTrigger()：手動執行一次，建立 4 小時 keepWarm 排程，防止 GAS 冷啟動，並清除過時的舊 Trigger。
  • setupAllOnEditTriggers()：設定主日、小組與事工三個試算表編輯偵測的 onEdit Trigger，讓手動編輯能即時更新 Firebase 快取。
  • firebaseCacheClearAll()：當發現 Firebase 資料與 Sheet 嚴重不同步時，執行此函數可強制清除所有 Firebase cache 暫存，迫使系統重新讀取試算表。
  • batchGenerateMissingQRCodes()：為沒有 LKXXXXX 編號的舊會友補齊編號。
  • batchGenerateAllMemberCards()：批次為所有會友產生個人名卡（存成 JPG 到 Google Drive）。支援超時自動中斷與斷點續跑，可安全在瀏覽器中手動多跑幾次直至 100% 完成。
